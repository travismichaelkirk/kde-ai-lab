# KDE AI Lab — v0.5 Local Security

## Purpose

Document the local-network security model and operational
verification of the KDE AI Lab HTTP bridge.

Baseline: v0.4-authenticated-bridge
Baseline commit: 76a7c34

## Architecture Decision

KDE AI Lab is a local development environment for Fedora
KDE Plasma and Android Tasker.

Remote connectivity is not required.

The existing authenticated HTTP bridge is retained as an
optional development tool rather than an always-on service.

No Tailscale integration, router port forwarding, HTTPS
proxy, or additional Android helper application is required
for the current workflow.

## Authentication

The bridge uses the HTTP request header:

X-KDE-AI-Lab-Token

Authentication uses a randomly generated 64-character
hexadecimal token.

Fedora stores the token outside the Git repository:

~/.config/kde-ai-lab/token

Tasker stores the matching token in:

%KDE_AI_LAB_TOKEN

The actual token must never be committed or included
in documentation.

## Operating Procedure

The Tasker profile is named:

KDE AI Lab HTTP Bridge

The HTTP listener uses TCP port 8765.

Normal operating state:

DISABLED

Enable the profile only when the HTTP bridge is needed
for development or testing.

Disable the profile immediately after completing the work.

## Verification Results

Test environment:

Fedora KDE Plasma
Pixel 11 Pro running Android 17
Local Wi-Fi network

Verified tests:

1. Disabled profile refused TCP connections: PASS
2. Enabled profile accepted HTTP connections: PASS
3. Request without authentication returned 401: PASS
4. Request with correct token returned 200: PASS
5. Profile disabled again: PASS
6. Final TCP connection attempt failed: PASS

The final test returned:

curl: (7) Failed to connect
HTTP Status: 000

These results verify the listener's observed behavior
at the tested Pixel Wi-Fi address and port.

They do not establish that every possible network
interface or exposure path has been audited.

## Known Security Limitations

HTTP traffic is not encrypted while the bridge is enabled.

The authentication token could be exposed to an attacker
capable of intercepting the HTTP request.

The bridge currently uses permissive CORS headers.

The HTTP 401 response may display an unusual reason phrase,
but the numeric status code is correct.

The bridge must not be exposed directly to the public
internet or used for sensitive remote operations.

## Security Strategy

Minimize the attack surface by keeping the HTTP listener
disabled when not required.

Preserve token authentication for temporary use.

Avoid unnecessary network services and dependencies.

Reevaluate transport encryption if the bridge becomes
a frequently used or permanently enabled service.

## Milestone Conclusion

The existing v0.4 bridge remains functional.

Authentication was verified after disabling and
re-enabling the Tasker profile.

The bridge was returned to its disabled state.

No new Android applications or network infrastructure
were required.

The v0.5 milestone establishes a documented,
local-only, disabled-when-unused operating model.
